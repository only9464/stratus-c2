# ADR-0005：HTTP 轮询是兜底，不是主通道

- 状态：已接受（2026-11）
- 影响面：通道选择、成本模型、客户端实现

## 背景

"植入体定时 POST 一次拿任务"是 VShell 一类的经典模型，实现最简单。但在免费额度下它是致命的：

```
100 台 × 86400 / 30s = 288,000 请求/天  >  100,000（免费上限）
```

也就是说：**30 秒轮询只能养 ~34 台**，超过就 1027。

## 决定

- **主通道 = WSS + DO hibernation**；
- HTTP beacon 只在 WS 不可用时启用，默认间隔 **300 s**，服务端可下压到 900 s；
- 心跳走固定字节串，由 `setWebSocketAutoResponse` 直接应答，**不唤醒 DO、不计 duration**。

客户端降级策略：WS 连续 3 次失败 → 切 HTTP（300 s）→ 连续 6 次成功 → 回 WS。

## 代价

| 代价 | 说明 |
|---|---|
| 客户端要维护两套传输 | 参考实现里 `transport` 已抽象（Go 版本先做 HTTP） |
| WS 会被中间设备/运行时更新打断 | 必须实现重连 + seq 续传（文档已写） |
| 心跳"零成本"限制了携带信息 | 固定串不能带时间戳；需要信息就用每 15 min 一次的"业务心跳" |
| 降级期实时性骤降 | UI 必须显示"当前通道 / 轮询间隔"，否则操作员会以为卡了 |

## 什么情况下推翻

- 升级到 Workers Paid（请求数无限）——即便如此，轮询的**延迟**仍不如 WS，不建议改默认；
- 目标网络明确阻断 WS，且只需要"分钟级"控制 —— 那就是 HTTP 兜底的目标场景，不算推翻。
