# ADR-0002：每个会话一个 Durable Object

- 状态：已接受（2026-11）
- 影响面：DO 设计、成本模型、故障隔离

## 背景

实时通道需要一个"能同时持有植入体 WS 和若干操作员 WS、并且能排队/去重"的协调点。
可选方案：单例 DO、D1 轮询、每会话一个 DO。

## 决定

**每会话一个 `SessionDO`**，命名空间用 `idFromName(sid)`。

它持有：implant WS、N 个 operator WS、未 ACK 任务（SQLite）、seq 高水位、状态与能力位。
它只做四件事：接 WS、转发帧、去重、把元数据异步写回 D1。

## 理由

| 维度 | 单例 DO | 每会话 DO |
|---|---|---|
| 吞吐 | 单线程 1,000 req/s 软上限，一台机器的终端风暴会卡住所有人 | 天然分片，互不影响 |
| 存储 | 单对象 1 GB（Free）成全局瓶颈 | 每对象 1 GB，只装自己的队列 |
| 计费 | 一个对象 24 h 全活跃 | 空闲会话可 hibernation，≈0 |
| 故障隔离 | 一个会话打爆 = 全部掉线 | 只影响自己 |

## 代价

| 代价 | 说明 |
|---|---|
| 全局列表不能靠 DO | 会话列表必须走 D1（`sessions` 表），DO 只存实时态 |
| 跨会话协作要额外一跳 | 多跳中继 = A 的 DO 调 B 的 DO（每跳计费） |
| 状态要可序列化 | hibernation 会重建对象，构造里不能有重活；计数要能恢复（`counters` 表） |
| 对象数量多 | 但免费计划对象数不限，只受请求/存储额度约束 |

## 什么情况下推翻

- 需要"全局限流"这类跨会话强一致操作 → 加一个独立的 `HubDO`（现在已经有，只做 nonce/presence）；
- 单对象 1 GB 被队列撑满 → 说明把文件内容塞进 DO 了，那是设计错误，不是要合并对象。
